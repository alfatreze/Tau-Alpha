# Pack watchdog: plan (2026-11-05)

Status: **W0, W1 and W2 DONE 2026-11-05 on branch `pack-watchdog` (host-proven only: RTL simulation with the real CPU; no fit, no Pocket); W3 (fit), W4 (Pocket) and W5 (docs) open. Results: section 10.** Owner decision 2026-11-05: "I want the watchdog, let's plan it in" (D-T15). Follows D-M20 (packs are protected by integrity and strikes). Needs an RTL change and a fit; nothing here is host-proven or fitted yet.

## 1. The problem
A pack is code from the card that the player calls once per picture (`pack_tick(&in)`, `fw2/ui/meters.c` around line 441). The host judges the tick only **afterwards** (`took = cycles() - tp`, `ps_judge`: three overruns disable the pack). A pack that never returns (an endless loop) hangs the whole player: no audio refill, no UI, nothing recovers except a power cycle. D-M20 records this as the known limit and names the cure: a hardware watchdog.

**Goal:** an endless or far-too-long pack tick is cut off, counted as a strike, and the player keeps running (audio included). **Not a goal:** defending against a deliberately hostile pack (it runs with full access; signing was assessed and not chosen, D-M20).

## 2. Facts from the tree (read 2026-11-05)
* The CPU is VexRiscv (`src/fpga/rtl/VexRiscv_Full.v`). It has `timerInterrupt`, `softwareInterrupt` and `externalInterruptArray[31:0]` inputs; `tau_soc.v` ties all three to 0 (lines 390-392).
* The firmware uses **no interrupts and no traps**: `fw2/platform/start.S` sets the stack, paints the sentinel, clears `.bss`, calls `main`; there is no `mtvec`, `mstatus` or CSR access anywhere in `fw2/`.
* The reset is global: `cpu_reset` (`core_game.vh` line 107) = reset counter, `fw_loaded`, host reset; it resets the CPU and every peripheral together. The firmware image is loaded into RAM once at boot and `.data` is initialised **in place** (no pristine copy). A CPU reset would therefore restart `main` with **dirty `.data`**: a reset is not a clean recovery.
* The existing check is soft and after the fact (`ps_judge`, `pack_strike_core.h`, host-tested); the per-pack limit `p2.max_cycles` is in the manifest (`cyc_limit_of`).

## 3. Options
| | Mechanism | For | Against |
|---|---|---|---|
| **A. Interrupt + recovery (recommended)** | A cycle counter in RTL raises a CPU interrupt when the armed limit passes; a trap handler abandons the tick and returns into the scheduler | Audio keeps running; no reboot; reuses the strike logic; small RTL | First interrupt use in this firmware (trap entry, context recovery); a pack that disables interrupts is not stopped |
| B. CPU reset on expiry | Counter resets the CPU | Stops anything | Restarts with dirty `.data`; the song stops; needs a reset-surviving "why" flag; no RAM budget for a pristine copy |
| C. A with B as a last-resort backstop | A, plus a reset if the interrupt is not acknowledged within N cycles | Catches a pack that masks interrupts | Needs the dirty-`.data` problem solved first; larger; decide after A is on a Pocket |

**Recommendation: A for the first version; C only if the owner wants protection against interrupt-masking code after A has run on a Pocket.**

## 4. Design of A
**RTL (`tau_wdog.sv`, about 50 ALMs, no RAM, no DSP):** a free-running 32-bit down-counter on `clk_sys` and four MMIO registers in the next free block of `tau_soc.v`'s map:
* `WDOG_ARM` (write): the limit in cycles; loads the counter and starts it. Writing 0 disarms. Not reset by the CPU's own writes, only by `cpu_reset`.
* `WDOG_STATUS` (read): bit 31 present, armed, expired (sticky until acknowledged), the expiry count.
* `WDOG_ACK` (write): clears `expired` and drops the interrupt.
* the interrupt line goes to `timerInterrupt` (level; stays up until acknowledged). Present bit lets old firmware and new bitstreams coexist (the usual `CORE_VERSION` / probe rule applies: use the runtime probe).

**Firmware:**
* `start.S`: a trap vector (`mtvec`) that saves the minimum, checks `mcause`, and for the watchdog interrupt jumps to a recovery routine. Anything else keeps today's behaviour (hang visible in the Report, not silent).
* The pack call site arms the counter just before `pack_tick` and disarms right after; `mstatus.MIE` is set only inside that window, so **no other firmware code ever sees an interrupt**.
* Recovery (the part with real risk): the call site saves `sp`, `ra`, `s0..s11` (a minimal `setjmp`); the handler acknowledges the watchdog, restores them and returns into the call site with "aborted". The call site then treats it as a strike, sets `force_next`, and **cleans the engine**: drain or flush the gfx command queue and fence state the pack may have left half-written (needs a check of what a safe flush is in `tau_gfx`/`tau_talos`; this is the main open technical question).
* An abort should count as **more than one strike** (suggestion: the pack is disabled for the session at once, since an endless loop is not marginal); the owner decides.
* The hardware limit is a multiple of the soft limit, with a floor and a ceiling (suggestion: 4 x `p2.max_cycles`, floor 2 M cycles, ceiling 200 M; **built with a ceiling of 20 M cycles (300 ms) instead, see section 10**); packs with limit 0 get the ceiling.
* Diagnostic Build only: a registered `P2_DIAG` feature (`fw2/diag_features.json`, `fw2/build.sh DIAG=1`) with a built-in "hang" test pack and Report rows `WDOG ARMS / EXPIRES / LAST LIMIT`. Counters in the normal build are cheap and stay.

## 5. Work, in order (each phase ends with a result)
* **W0 Facts (host, small):** confirm VexRiscv_Full was generated with the interrupt and CSR plugins on (the ports exist; check `mtvec`/`mie` are really present); decide the safe engine flush; read `tau_gfx` for what a mid-command abort leaves behind. Output: this plan's open questions answered.
* **W1 RTL + host test:** `tau_wdog.sv` + an iverilog testbench (arm, expire, ack, disarm, limit 0, re-arm during expiry, reset) with mutants, per the repo's red-then-green rule.
* **W2 Firmware + host test:** trap entry, the recovery routine, the call-site change, a pure core for the limit arithmetic (like `pack_strike_core.h`), a host test of the strike logic; a CPU-level simulation of the trap path if the repo's firmware-in-RTL harness can run it (check in W0), otherwise the Diagnostic Build hang test is the first proof.
* **W3 Fit:** one RTL change = one fit, about 1 h 40 per seed, two seeds for any timing claim (about 3 h 30). The player fit is at hold +0.096 ns and has only one seed (`rc-b936-s2` is queued): do not add to the RTL until that second seed is read.
* **W4 Pocket:** a Diagnostic Build with the hang pack: the tick is cut off, the song keeps playing, the pack is struck out, the Report shows the counters; then a normal pack still runs with a clean count. Evidence labels as usual; nothing claimed before that run.
* **W5 Docs:** D-M20 follow-up, `pack_strike_core.h` comment (no longer "no watchdog"), the pack author guide (a pack that never returns is cut off), audit entries.

## 6. Where it fits
`V0_7_0_REVIEW.md` says not to add a pack-safety hardware watchdog to v0.7.0 (it needs a new bitstream), and the v0.7 RTL (`rc-b936`, DEV 202) is already fitted and tested. So this goes in the **next RTL fit after v0.7.0**, bundled with whatever else needs RTL by then. W0 to W2 are host work and can start any time without touching the fitted bitstream.

## 8. Risks
* Recovering from an interrupt in the middle of an engine command or an MMIO burst may leave the engine in a state the host does not expect; this is why W0 and the W4 hang test exist.
* A pack that writes `mstatus` or `mtvec` defeats A (accepted limit; the same pack can already do anything).
* First use of interrupts: the trap path must be proven by a test that actually takes the interrupt, not by reading the code.

## 9. W0 results (2026-11-05, read from the tree; nothing run)
1. **The CPU can take the interrupt.** `VexRiscv_Full.v` carries the machine-mode CSR plugin with `mtvec` (0x305), `mstatus.MIE` (0x300), `mie` with the timer and external enables (0x304: `MTIE`, `MEIE`), `mip.MTIP`, `mepc` (0x341) and the `mret` jump; an interrupt is taken when `mstatus.MIE` is set. The reset vector is 0 (`externalResetVector`), so the trap vector must be set by software. **Use `timerInterrupt` (`mip.MTIP`)**: nothing else drives it today (`tau_soc.v` ties it to 0).
2. **The engine cannot be flushed, only drained.** There is no abort or queue-clear register: `R_FB_GO` takes one command per write (each write is atomic), the queue drains by itself, and `R_GFX_STATUS` bit 16 says idle. So an aborted tick leaves only commands that were wholly accepted; they finish. What breaks is **host-side shadows** in `fw2/gfx/gfx.c`: `color_shadow`, `base_src` / `base_dst` (the "unknown" sentinel is 0xFFFFFFFF), `hw_fence_issued` (against the `R_GFX_FENCE` count) and the double-buffer index `cpu_buf`. An abort between a shadow update and its register write would leave a shadow that lies, and the next command would skip a write it needs. **Recovery rule:** after an abort, wait for engine idle with a time limit, then reset the shadows to "unknown", reconcile the fence counter, and force a full repaint (`force_next`, which the call site already does after a strike).
3. **The real CPU can be simulated with firmware.** `sim/build_fw.sh` builds a small bare-metal image, and the Makefile runs it on `tau_soc` with the real VexRiscv (example: `tb_gfx_status_soc.v` + `sim/fw_gfxstat/main.c`, pass = a "PASSED" line). So W2's trap path can be **proven in RTL simulation** with a `fw_wdog` image that arms the watchdog, spins forever, takes the interrupt, recovers and prints PASS, plus mutants (interrupt not acknowledged, MIE left set, shadows not reset). No Pocket is needed for the first proof.
4. **Still to check in W1/W2:** the exact free MMIO addresses for the four registers (the map in `tau_soc.v` and `fw2/platform/mmio.h`), and that `start.S` can set `mtvec` without moving the stack paint or the `.bss` clear.
**Effect on the plan:** option A stands, and the engine question (section 4) is answered by the recovery rule in item 2. Next: W1 (RTL block and testbench), which needs no decision from the owner beyond the four in section 7.

## 10. W1 and W2 results (2026-11-05, branch `pack-watchdog`; host-proven, NOT fitted, NOT on a Pocket)
**W1, the RTL block.** `src/fpga/core/tau_wdog.sv` (cycle-counting watchdog, sticky interrupt, contract in its header), wired into `tau_soc.v` as the CPU's `timerInterrupt` with the parameter `WDOG_ENABLE` (registers `R_WDOG_ARM` 0x1DC write, `R_WDOG_ST` 0x1E0, `R_WDOG_ACK` 0x1E4 write, `R_WDOG_CNT` 0x1E8; the arm strobe is registered, so the limit counts from one clock after the write). Built only with the macro `TAU_WDOG` (`core_game.vh`); **the shipped bundles do not define it, so their bitstreams are unchanged** (with 0 the registers read 0 and the interrupt input stays tied to 0). Listed in `ap_core.qsf`. `make test-rtl-wdog`: directed cases that pin the contract (exact timing, sticky until ack, disarm, re-arm, the arm-in-the-end-cycle race, ack and arm together, a 70,000-cycle limit, reset) plus 200,000 random cycles against an independent reference model; 6 mutants, all killed.
**W2a, the trap path on the real CPU.** `fw2/platform/start.S` now sets `mtvec`, and holds `trap_entry`, `wd_save` / `wd_resume` (a minimal setjmp) and `wd_irq_on/off`. `make test-rtl-wdog-soc` links `sim/fw_wdog/main.c` with that **production** `start.S` and runs it on `tau_soc` + VexRiscv: 14 checks (a tick that finishes in its window never traps; an endless tick is cut off after the limit plus the trap latency, 3000 to 3400 cycles for a limit of 3000; the handler alone closes the window; callee-saved registers and the stack pointer come back; a second cut works; no interrupt outside the window; a timer interrupt with the window flag clear restarts the firmware; any other trap restarts it, as the unset `mtvec` did). 5 `start.S` mutants (no acknowledge, window left open, registers not restored, no window flag, other traps spin) and the cut interrupt line are all killed.
**W2b, the player.** `fw2/platform/platform.c` `wd_run(limit, fn, arg)` (arms, opens the window, calls the tick, closes; on a cut it calls `gfx_recover()`), `fw2/gfx/gfx.c` `gfx_recover()` (waits for the engine to go idle, at most 50 ms, then resets the colour and base-pair shadows to "unknown", reads the fence count back, rewrites the drawing-buffer register from its shadow), `fw2/cores/pack_strike_core.h` `wd_limit()`, and the call site in `fw2/ui/meters.c`: a cut pack is struck out at once (status `MPK_E_STRIKE`, `PACKS STRUCK` + 1, a full repaint is forced) and the built-in code draws from the next picture. A bitstream without the watchdog just runs the tick (probe: `R_WDOG_ST` bit 31). `sim/test_p2_wdog.py` (window arithmetic with an overflow mutant; the strike path through the real `meters.c`; a mutant that ignores the cut) passes; the existing strike test needed one pattern fixed.
**Decisions taken in the build, for the owner to confirm (plan section 7):** (1) an abort strikes the pack out at once: implemented. (2) The hardware window is 4 x the soft limit, floor 2 M, **ceiling 20 M cycles (300 ms), not 200 M**: the audio ring holds about a second, so a 3 s cut-off would already have underrun; a soft limit of 0 gets the ceiling. (3) Option A only; no reset backstop.
**Hot RAM, the finding that shaped the code.** The Diagnostic Build (`DIAG=1`, `PACKS=1`) had **96 bytes** above the 1,024-byte floor before this work (the normal build 2,752). The watchdog's helpers (`wd_run`, `gfx_recover`, `wd_save`, `wd_resume`, `wd_irq_on/off`) therefore live in the cold (PSRAM) image (`P2_COLD_TEXT`); only `trap_entry` and a few words are hot. Result: hot cost 96 bytes; **normal build 2,656 spare, Diagnostic Build exactly 0 spare** (it links, at the floor). To get there the `PACKS CUT` Report row and its `meter_stats` counter were left out (they cost 28 bytes the Diagnostic Build does not have): cuts show as `PACKS STRUCK` and the Info `PACK ERR 40`. **The Diagnostic Build has no margin left for anything else**; a feature moved to cold code or dropped is the way to get it back (rule 5, never lower the floor).
**Still open:** W3 the fit (one RTL change = one fit, two seeds, after the second `rc-b936` seed and the v0.7.0 release; the shipped fits do not define `TAU_WDOG`, so a watchdog fit needs its own bundle with the macro); W4 the Pocket test with a hang pack (needs a registered `P2_DIAG` test pack, not built yet); W5 the docs (D-M20 follow-up, the pack author guide); whether `P2_PACKS` firmware must also check `CORE_VERSION` for a watchdog bitstream (the runtime probe is used instead, as for other optional units).
