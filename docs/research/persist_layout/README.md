# Persisted settings: golden vectors and real captures

* `golden_vectors.json`: legacy register files and the register files the migration writes (words 0..31, only the non-zero ones), with the values they hold, plus migrations interrupted after k writes and what the next boot makes of them. Made by `python3 tools/persist_layout.py --golden docs/research/persist_layout/golden_vectors.json`; the Python reference `tools/persist_layout.py` is proven equal to the firmware's C code over random register files by `sim/test_persist_layout.py`.
* `captures/devNNN_interact_persist.json`: the real `Settings/<core id>/Interact/_core/interact_persist.json` of four cores of the owner's card (the Pocket's own files, untouched): **TAU DEV 181** (legacy layout: word 0 is the volume, 15 variables, ids 24-26 absent from this build), **TAU DEV 182, 183 and 184** (new layout: word 0 carries the layout version in bits 30..27, 16 variables incl. id 33).
  **These are NOT a before/after of one migration.** The Pocket keeps the settings of each core in its own folder, and a DEV build is a new core id, so DEV 182 started from an empty file (the new defaults), not from DEV 181's. They are real examples of each layout, written by the Pocket. Decode any of them: `python3 tools/persist_layout.py <file>`. A real before/after of the migration needs one core whose folder holds a legacy file while the new firmware runs (B-842 proposes the test).
