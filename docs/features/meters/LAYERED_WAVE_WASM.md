# Layered Wave as WebAssembly (B-959; phase 1 done 2026-11-06, host-simulated)

**Why.** The meter lab (`tools/meters/preview`) and Tau Omega (Rust, Svelte, Tauri) preview Layered Wave with a hand-written JavaScript twin (`meters/layered_wave.js`) of the firmware's C (`fw2/ui/layered_wave.inc`). Every change to the meter had to be written twice and held together by the 1.9 M-command golden test (B-957, B-958 touched both sides each time). Sound Map already avoids this: its lab twin is the firmware source compiled to WebAssembly. Owner decision (2026-11-06): do the same for Layered Wave.

**Phase 1 (done).** `tools/meters/preview/wasm/layered_wave_wasm.c` includes the firmware's own `fw2/ui/meter_layered_wave.c` (so `layered_wave.inc`) and is built by `tools/meters/preview/wasm/build_wasm.py layered_wave` (Homebrew llvm + lld: `clang --target=wasm32` and `wasm-ld`) into the committed `tools/meters/preview/meters/layered_wave_wasm.js` (24 KB of wasm, base64, with the SHA-256 of every file it was built from; nobody else needs the toolchain). `sim/test_layered_wave_wasm.py` (in `make test-host`, needs node): the module is current, and **it draws exactly what the JS twin draws, 1,211,485 commands in 125 scenarios** (every golden scenario: presets, grids, colours, the experimental group, setting changes, forced repaints, a moved box, fullscreen); a control with another taper is reported as a mismatch. The staleness check now covers exactly the files the module includes (the compiler's own `-MM` list is recorded in the committed module), for Sound Map too.

**Interface of the module** (what Omega's Svelte code and the lab call; nothing else is exported):
* imports (`env`): `rect(x, y, w, h, rgb565)`, `scroll_left(x, y, w, h, d)` (the SCROLL view: copy the box left by d columns, leave the right d columns as they are; the caller of the module implements it on its framebuffer), `text(...)` (only "LAYERED WAVE UNAVAILABLE", never reached in the browser).
* exports: `memory`; `in_ptr()` the `mtr_in_t` (fields written at the byte offsets from `offs_ptr()`, in this order: x y w h bg force paused degrade frame dt_ms peak_l peak_r; widths 2 2 2 2 2 1 1 1 4 2 4 4); `spec_ptr()` 16 bytes (the band levels, 0-255); `wave_ptr()` and `n_wave()` (256 signed bytes, the waveform; only the DYNAMICS split reads it); `params_ptr()` and `n_params()` (u16 per parameter in the order of `meters/layered_wave/meter.json`, i.e. the generated `MP_LAYERED_WAVE_*` enum); `roles_ptr()` and `n_roles()` (u16 per theme role, the `TR_*` order of `fw2/ui/theme.h`, accent included); `tick()` (one picture as the Player 2 firmware makes it: the DYNAMICS waveform is the loudest peak as a flat envelope) and `tick_raw()` (one picture with the waveform as written, for parity tests).
* behaviour: one instance holds one meter's history; a new instance is a fresh meter. The cost guard counts commands (the Pocket counts CPU time, which a browser cannot model), like the golden test's C build. Compile asynchronously (`WebAssembly.compile`), as `meters/sound_map.js` does.

**Phase 2 (done 2026-11-07, B-975, host-simulated).** (1) `meters/layered_wave.js` is now an adapter: `tick` maps the lab's theme (21 roles), parameters (the module's own key list, `params` in `layered_wave_wasm.js`, written by `build_wasm.py` from the generated enum), spectrum, waveform and box onto the module and runs `tick_raw`; the engine calls land in `rect`, `blit` and the new `scrollLeft` of `tau_fb.js`. In node the compile is synchronous (the tests and `Run.run` need no waiting); in a browser `ready()` compiles asynchronously and a tick draws nothing until then. The drawing code of the JS twin (history, spectrum, curve, windows, interpolation, ballistics) is deleted: what stays is lab help that is not drawing (`targets`, `boundsFor`, `bandOwner`, `describe`, `ends`, `layerColours`, checked by `tools/meters/preview/test.js`). (2) `golden_lw.js` takes its logs from the module through the adapter and `sim/test_layered_wave_golden.py` compares them with the native C (Diagnostic and main build): 2.01 M commands, now including the SCROLL view (both Directions, both draw modes, taper, curve profile, short tail, full box, a view change and a Direction change mid-run). `sim/test_layered_wave_wasm.py` drives the module directly (`wasm/parity_lw.js`, no lab code) and compares with the adapter's logs, which proves the mapping. The JS twin of the drawing ceases to exist: a change to `layered_wave.inc` needs `build_wasm.py layered_wave` and nothing else. (3) The lab previews SCROLL (checked in the lab page in a browser: the picture scrolls with the taper). (4) Extras (B-977, 2026-11-07): a second build of the same source, `layered_wave_timed_wasm.js` (`-DWASM_TIMED`: `LW_TIME_GUARD`, the guard counts CPU time as on the Pocket), whose `clock` import is a MODELLED cycle counter (5,000 cycles = 75 us per engine command, the middle of the 60-90 us a redraw costs on the Pocket; a model, not a measurement); the lab has a checkbox "CPU-time guard (model)" (`ctx.timed`; a fresh meter on change); the plain build stays what the golden test compares with the native C. The module exports `ebounds_ptr`/`ebounds_ok`/`stride`, so the lab's split map shows the ENERGY split's learned boundaries. (5) The lab page grew from 158 KB to 183 KB, and to 220 KB with the timed build.
