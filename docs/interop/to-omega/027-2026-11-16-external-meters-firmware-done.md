## A027/1 · Status
**The owner decided to keep the feature.** Built, merged and **tested on a Pocket (TAU DEV 224, music playing)**: the table of contents of up to 64 rows read at boot; one execution window, a pack loaded only when its meter is selected (typical 36 to 39 ms, the biggest pack at worst 111 ms, no dropout counter moved over about 130 swaps); the settings (selected meter by `id_hash`, its preset, tunings keyed by hash and `params_rev`) saved by the Pocket on Quit; the commit rule and safe boot (a meter that hangs is cut by the watchdog, and after a restart the player is back on the last meter that ran cleanly: confirmed twice); the Settings METER list scrolls through all rows in the same order as X on Now Playing, greys a row this firmware cannot run, hides rows flagged hidden; the preset files are listed for meters with a folder. Not covered yet: a hang that needs a power cycle, a hostile pack, a larger real library, the release packaging (our P2.6).

## A027/2 · What is ready for you (read side first, as agreed in 024)
- **The bin v2:** the Python reference `tools/meter_bin.py`, the C reader `fw2/cores/meterbin_core.h`, and the golden vectors in `docs/research/meter_bin/` (the bins, `expected.json` with, for every vector, the code the firmware answers at boot (`boot_code`) and the code of the full check (`code`), and a README with the SHA-256 of every file and what is real and what is synthetic). Header is **40 bytes with a `toc_crc`**; the whole-file CRC is for tools only; the firmware reads v2 only (spec sections 2 and 3, A026).
- **`persist_layout` 2:** the mirror `tools/persist_layout.py`, `docs/research/persist_layout/golden_vectors.json`, the staged legacy captures in `staged/` and `captures/`, with a README (your O021/3 item 7). A layout-2 card is read only for Omega until your mirror ships.
- **`tau-compat.json`** (every release package from now on): `requires_omega` carries `persist_layout` 2, `packs_abi` 1 and `packs_abi_minor` 2, and `Assets/tau/common/tau-meters.bin` is listed as a **user file** (format `TPKB` v2, at most 4,456,448 bytes), never shipped in a zip.
- **The seven shipped meters' ids** (fixed, 128 random bits each) are in `meters/<key>/meter.json` (`id`); the firmware table is `fw2/cores/shipped_meter_ids.h`.
- **Please run your reader against the vectors** and tell us any vector where your code differs from `expected.json`; that is the only thing we need from you before you start composing.

## A027/3 · Behaviour you need for the composer
- The firmware prefers the user bin `Assets/tau/common/tau-meters.bin` when it is sound, else the core's own `tau-packs.bin`. A bin with **no fallback row** (flag bit 1, Winamp Bars, listed first) is refused whole (code 20): always compose it in.
- A row the firmware cannot run (`abi` or `tau_min` above its own) is listed greyed and cannot be picked; a row flagged hidden is not listed and X skips it; rows whose `id_hash` shares its **low 16 bits** with another row keep working but lose tuning: tell the user at compose time (A026/4).
- Presets: `tau-presets/<first 8 hex digits of the id>/` is preferred; for the seven shipped meters the old decimal folders (12 to 18) are still read when the hash folder is absent; the METR section of `tau-assets.bin` applies to pack meters again (by manifest id). Moving the decimal folders to the hash names is yours when you compose.
- **The user bin only has an effect on a core that declares data slot 10.** Today that is the DEV builds; the release `data.json` gets it in our P2.6. So a v0.7.x TAU ignores `tau-meters.bin`, and Omega must not offer a meter install for a core that does not read it. **The owner delegated the shape of the capability to us (A027/Q-1, decided): there is no new key.** The capability is already in each package's `layout` in `tau-compat.json`, generated from the package's own `data.json` and the firmware's format table, so it cannot disagree with the core: a core reads a user meter bin **if and only if its package `layout` has an entry with `role` `user`, `slot` 10 and a path ending `/common/tau-meters.bin`**; its `format` says what it reads: `{"name": "TPKB", "version": 2, "max_bytes": 4456448}` (the highest bin version, and the size limit). **No such entry = the core ignores the file** (both v0.7.1 packages have none; every DEV 220 and later package has it). Example, from `TAU DEV 224`: `{"path": "Assets/tau/common/tau-meters.bin", "role": "user", "slot": 10, "required": false, "format": {"name": "TPKB", "version": 2, "max_bytes": 4456448, "preserve_unknown_sections": false}}`. Reason for this over a boolean, a slot id or a separate version key: one source of truth (the same JSON the firmware is built from), already shipped, and per core (TAU, Diagnostics, Preview can differ). From P2.6 the release packages carry the entry too. If you see a reason this is not enough for your guard, say so.
