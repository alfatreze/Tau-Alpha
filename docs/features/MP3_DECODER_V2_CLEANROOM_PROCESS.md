# MP3 decoder v2: clean-room process (2026-11-25)

**Audience: the coordinator, the contract author and the verifier. This document, `MP3_DECODER_V2_SCOPING_2026-11-25.md` and `MP3_DECODER_V2_REQUIREMENTS.csv` describe Helix internals and MUST NOT be given to the implementer.** Rule 7 of `docs/PROJECT_RULES.md` (no copyleft code) and decision D-P01 apply; the project is MIT. Helix is RPSL: it is read for measurement and used as a test oracle only, never copied or adapted. This process extends the one proposed for Talos (`TALOS_ENGINE_V2_CLEANROOM_PROCESS.md`).

## 1. Roles
| Role | May see | Must not see | Produces |
|---|---|---|---|
| Contract author | the standards' formulas, the test data, Helix measurements and structure (already seen by the scoping session) | writes no decoder code | behavioural contract, float64 reference model (Python), stage golden data, vector list |
| Implementer (a fresh agent or person per stage) | the contract, the standards-derived formulas and data tables the contract names, the host harness API, the project's coding style and `fw2/cores/*_core.h` examples of other cores | Helix source or headers, the scoping report, the requirements CSV, any decoder derived from Helix (FFmpeg, mpg123, libmad, LAME, libhelix forks); minimp3 source (CC0, but see 3) | the fixed-point C decoder and its tests |
| Verifier | everything | edits the decoder | Helix oracle runs, similarity audit, conformance results, audit entries |

The implementer's worktree must not contain `third_party/libhelix-mp3` (a worktree branch that removes it, or a sparse checkout), nor `docs/features/MP3_*SCOPING*`, nor `tools/mp3_v2_measure/`. The verifier checks this before each hand-over and records `git ls-files` of the implementer's tree.

## 2. What the implementer receives (the package)
1. The behavioural contract: for each stage its inputs, outputs, formats, ranges and error behaviour, stated as behaviour (what comes out for what goes in), not as an algorithm skeleton from any implementation. Frame-level API (one frame in a linear buffer, trimmed pairs out, rate tag, error codes, resync rules, reset/keep rules across discontinuities and gapless joins), resource limits (RAM, stack, per-frame time) and the unit handshake (`fw2/decode/poly_hw.c` API, already ours).
2. The standards' behaviour, as formulas the contract author transcribed (ISO/IEC 11172-3 and 13818-3): requantisation formula, antialias butterflies, IMDCT and window definitions, stereo processing, the frame/side-info bit layout.
3. The data tables (section 3) as files with provenance headers.
4. The float64 reference model and the stage golden data (the implementer may read the reference model, which is the contract author's Python written from the standard).
5. The vectors, the harness, the tolerance rule.

**Rule:** never read a decoder's source "for the table". Where minimp3 is the source of a table, the extractor reads the table data only (as B-1168 did), and the exact lines read are recorded. Anything else read is recorded in `docs/PROVENANCE.md` as inspiration.

## 4. Similarity audit (run by the verifier, at every stage hand-back and before deletion)
* **Method.** Tokenise the new C (comments and whitespace removed, identifiers and numeric literals normalised), take k-gram fingerprints (k = 12 tokens, winnowing window 8) and compare with the same fingerprints of: every file of Helix (`third_party/libhelix-mp3`), minimp3, and any other source the contract author read. Also compare the declaration structure (function and struct count, parameter lists) and the data tables as bytes.
* **Thresholds (proposed, to be fixed at P0).** (a) Any run of 12 consecutive matching tokens outside the declared allow-list (standard constants, table data, trivial idioms such as loop headers) is a finding to be explained in writing; (b) whole-file fingerprint overlap above 5 % against any one source is a failure; (c) identical function names or struct field names that are not dictated by the standard are a finding; (d) tables are allowed to be equal where they come from the standard or a recorded permitted source, and nowhere else.
* **Evidence recorded** per stage in the audit trail: tool version and parameters, the comparison output (hash of the report), findings and their resolutions, the implementer's tree listing (proving Helix absent), the date and time of access to each permitted source, and the commit ids. A failed audit sends the stage back to a new implementer who receives the contract and the finding class, not the matching lines.

## 5. Process rules
* The implementer works on its own branch and worktree; the contract author and verifier on others (rule 1). Commits as the owner, no AI attribution (rule 9).
* The verifier never tells the implementer what Helix does; discrepancies are reported as a failing vector, an input and the expected float-model output.
* Helix output is never used as the expected value of a stage test; stage tests use the float model and the standard. Helix is used for the end-to-end differential and for performance comparison only.
* Honour-based separation is the weakest part; the technical separation (worktree contents, tree listing, fingerprints) is what the audit entries must show.

## 6. Evidence to record (checklist for each audit entry)
Sources used with licences and hashes; extractor scripts and their outputs; the implementer's tree listing; similarity report; conformance and differential results with RMS/max; which parts were measured on a Pocket and which not.
