## 2. What minimp3 stores in a transformed form, and how it was expanded [READ]

| minimp3 | form | expansion here |
|---|---|---|
| `tabs[]` (2,164 `int16`), `tabindex[32]` | the 32 big_values code tables as two-level lookup tries: first level 5 bits, negative "pointer" entries (`-(offset*8) + width`), entries replicated 2^(5-len) times for short codes, a leaf word `(len << 8) | (second value << 4) | first value`; the length in a sub-table counts only the bits of that level | the extractor walks the tries back into explicit lists `(code, length, x, y)`, asserts that every replica is identical, the code is prefix free and its Kraft sum is exactly 1; selectors 16..23 and 24..31 share a trie (`tabindex` 1460 and 1842); 0, 4, 14 point at an all-zero table (no bits) |
| `tab32[28]`, `tab33[16]` | count1 tables A and B: a 4-bit first level with pointer entries (A) or a flat 4-bit table (B); leaf word `(v w x y) << 4 | 8 | length` | expanded to 16 quadruples each, then written as flat 6-bit (A) and 4-bit (B) direct lookups |
| `g_scf_long[8][23]`, `g_scf_short[8][40]`, `g_scf_mixed[8][40]` | one row per minimp3 sample-rate index (`my_rate - (my_rate != 0)`: MPEG-1 rows 5..7, MPEG-2 rows 2..4, MPEG-2.5 rows 0, 0, 1), widths with a 0 terminator, short bands repeated three times, rows shorter than the declared width (zero padded) | one row per rate in our order (MPEG-1 44.1, 48, 32; MPEG-2 22.05, 24, 16; MPEG-2.5 11.025, 12, 8): long widths `[9][22]`, short widths `[9][13]` (one entry per band), mixed rows verbatim `[9][40]` plus the count of long entries `[9]` (8 for MPEG-1, 6 for LSF) |
| `g_scfc_decode[16]` | `(slen1 << 2) | slen2` | `slen1[16]`, `slen2[16]` (slen1 reaches 4: the value is 5 bits) |
| `g_preamp[10]` | pretab for bands 11..20 only | the standard's 22-entry pretab |
| `halfrate[2][3][15]` | kbps / 2, layers indexed by the header field (III is index 0, not 2) | layer III bitrates `[2][15]` in kbps |
| `g_pow43[145]` | sign x^(4/3), x = -16..128, 6-decimal floats; the negative half is indexed by the magnitude (offset 0), the positive by 16 + x | the extractor checks the table against the formula (max relative error 7.6e-8) and emits the formula: `round(x^(4/3) 2^22)` for x = 0..128 as `uint32` (Q22 is provisional, pending WP-12) |
| `g_expfrac[4]`, `g_pan[14]`, `g_aa[2][8]` | float constants | checked against 2^-30 2^(-k/4), tan(p pi/12)/(1+tan), 1/sqrt(1+c^2) and c/sqrt(1+c^2) (c = the standard's eight values) to 1e-7; emitted from the formulas as Q30 / Q31 |
| `g_scf_partitions[3][28]`, `g_mod[24]` | LSF scale-factor partition sizes and moduli | verbatim (`mp3v2_lsf_partitions`, `mp3v2_lsf_mod`), with minimp3's row indexing documented in the header |

Not extracted (back-end data is generated from formulas for WP-16, not copied): `g_win` (the window is in the unit and in `tools/data/mp3_synthesis_window.txt`), `g_mdct_window`, `g_twid9`, `g_twid3`, `g_sec`: the header holds the standard's IMDCT windows `sin(pi/36 (i+1/2))` (18 values) and `sin(pi/12 (i+1/2))` (6 values) in Q31 and the alias coefficients cs, ca in Q31 [F]. The derivation of the IMDCT factorisation and its twiddles belongs to WP-16.

## 3. Our Huffman layout [DERIVED]

`int16` entries; a leaf is `(n << 8) | (x << 4) | y` with `n` the bits consumed at that level, a pointer is `0x8000 | ((w-1) << 12) | offset`; every selector has a base offset and a first-level width (`mp3v2_huff_base[32]`, `mp3v2_huff_w1[32]`; width 0 for the three empty selectors). The levels are built from the explicit code lists by a dynamic programme (per node, the width 1..8 with the smallest total). First level 5 bits: **2,053 entries, 4,106 bytes** (minimp3: 2,164 entries, 4,328 bytes). The size for other first-level widths is in the header (3: 1,843, 4: 1,901, 5: 2,053, 6: 2,401, 7: 3,041, 8: 4,223 entries); 5 was chosen because most codes then resolve in one or two lookups; 3 bits is 8 % smaller and needs more levels per code (the decoder work package WP-13 may change the constant with `--l1`; the tests do not depend on it). The decode loop is written in the header.

## 4. Structural findings [MEASURED]

- **Every codebook is complete: Kraft sum exactly 1 for all 29 non-empty selectors (16 distinct codebooks), prefix free.** Code counts equal (xmax+1)^2 with the standard's xmax: 4 (table 1), 9 (2, 3), 16 (5, 6), 36 (7, 8, 9), 64 (10, 11, 12), 256 (13, 15, 16..31); every (x, y) of the square occurs exactly once. Maximum code lengths: table 1: 3, 2/3: 6, 5: 8, 6: 7, 7: 10, 8: 11, 9: 9, 10/11: 11, 12: 10, 13: 19, 15: 13, 16..23: 17, 24..31: 12. Linbits per selector 16..31: 1 2 3 4 6 8 10 13 4 5 6 7 8 9 11 13 (equal to the standard's list [MEMORY]).
- count1: table A has 16 codes, maximum length 6, Kraft 1 (the code `1` is the zero quadruple); table B is the 4-bit code with the value bits inverted.
- Band widths: long rows sum to 576, short rows to 192 (x3 = 576), mixed rows to 576 counting each entry as stored, for all nine rates. The 44.1/48/32 kHz long rows and the 44.1 kHz short row equal the standard's printed values [MEMORY].
- **Quirk (8 kHz mixed row):** minimp3's `g_scf_mixed` row for MPEG-2.5 8 kHz (`12,12,12,4,4,4,8,8,8,12,...`) does not have the shape "6 long entries, then 10 short bands x 3" of the other rows (its 39 entries sum to 576 but its first six sum to 48 lines, while the decoder switches 4 subbands = 72 lines to long for that rate). The row is kept verbatim and the test excludes it from the shape check; mixed blocks at 8 kHz are not in the owner's library and are almost certainly unused anywhere. Recorded for WP-13 (a decision: keep, or generate that row from the standard).
- **Identity:** the codes recovered from OUR layout equal, for each of the 32 selectors, the codes recovered from minimp3's own tries (test check per selector).
- **Round trip with the oracle [MEASURED]:** the test encoder (written in the test from the generated tables only) builds 16 MPEG-1 frames: every code of every selector once (chunks of at most 4,000 bits for the 12-bit `part2_3_length`; escape values with random linbits, including the extremes 0 and 2^linbits - 1; random signs), the zero table, and count1 A and B with all 16 quadruples and signs. The stage dump of the oracle (`tools/mp3_v2/oracle.c --stage`, WP-06) must equal `sign |q|^(4/3) 2^((gain-210)/4) / 2` on every line: worst relative error 9.2e-8 (|q| < 129) and 1.2e-6 (escape values; see below). This also fixes the factor 1/2: **minimp3's requantised spectrum is exactly half of the standard's** (`BITS_DEQUANTIZER_OUT` is -1); the factor is repaid by its synthesis stage.
- **minimp3's own requantisation error [MEASURED by emulating the interpolation of `L3_pow_43` in float32 for every |q| from 129 to 8,206; the formula is from my reading of the code, nothing is copied]: up to 1.31e-6 relative at |q| = 1,055, above the 2^-20 = 9.5e-7 requantisation target of the plan's WP-12.** The table part (|q| < 129) is within 7.6e-8. Consequence: a fixed-point decoder that meets 2^-20 against the exact formula will differ from float minimp3 by up to 1.3e-6 on escape values; WP-12 should define the requantisation target against the exact formula (the model), not against the oracle.

## 5. Size against the plan's table budget [MEASURED]

The generated header, compiled for rv32 (`riscv-none-elf-gcc -march=rv32im -mabi=ilp32 -Os`, every array referenced; the 24-pointer probe is subtracted): **5,998 bytes of `.rodata`**, the plan's budget "about 6 KB" (Huffman about 4 KB, band tables 0.8 KB, pow43 0.6 KB, windows/twiddles/antialias/DCT constants about 0.7 KB) against Helix's 12.6 KB. Breakdown: Huffman lookup 4,106 + selector tables 128 + count1 80 = 4,314; band tables 684 (long 198, short 117, mixed 360 + 9; the plan's 824 B was minimp3's padded form); LSF scale-factor tables 108; pretab, slen, bitrates and rates 132 (the sum, 5,986, is 12 bytes short of the measured total: alignment); pow43 516; Q30/Q31 constants (expfrac 16, pan 56, alias 64, windows 96) 232. Nothing for the IMDCT twiddles yet (WP-16), so the table total will grow by a few hundred bytes. Host build: `cc -std=c11 -Wall -Wextra -Werror` clean; rv32: `-Wall -Wextra -Werror` clean.
