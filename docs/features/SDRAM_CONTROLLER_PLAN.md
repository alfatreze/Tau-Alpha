# The shared SDRAM controller: review of Tau V's requirements and the plan (2026-10-28)

Status: **plan, nothing built.** Inputs: Tau V's `tau-nu/.claude/worktrees/codec-alternatives/docs/SDRAM_CONTROLLER_REQUIREMENTS.md` (v1, 2026-10-28, read in place), the Talos 2 documents (`TALOS2_REIMPLEMENTATION_PLAN.md` section 7, `docs/research/TALOS2_PLAN_REVIEW_2026-10-26_EXHAUSTIVE.md` R6 and R8), decisions D-T01, D-T06, D-T07, and what DEV 195..198 measured. Owner direction (2026-10-28): move the controller up the order (it was last and optional, D-T01/D-T06) and make it one controller shared with Tau V, whose video decoder needs more from it than the player does; recorded as D-T08.

## 1. Why this is worth doing for the player too
* Tau V measured the current controller (`tau_sdram_ctrl`, closed page, a refresh before every read) at n + 19 cycles per read and n + 11 per write of n words; our own T0 review reached the same arithmetic. For the player's long row bursts (128 to 400 words) that is a 5 to 15% overhead; for short accesses it is large: the CPU window access costs about 50 cycles net and 360 to 373 under scanout plus drawing (KB-030), and a one-pixel command still pays the whole open/close/refresh cycle. Open-page, bank-interleaved scheduling with distributed refresh should cut the CPU window latency and the engine's non-burst work most. **Honest estimate (not measured): the player gains tens of percent on CPU window latency and a smaller single-digit to low-double-digit percent on engine row time; Tau V gains the difference between not fitting (138% of 100 MHz) and fitting (60%).** The measurements of DEV 195..198 say the player's graphics cost today is firmware arithmetic and the engine's pass count, not the controller, so the controller is not the player's bottleneck; the case for doing it now is Tau V, provenance (D-T01: `tau_sdram_ctrl` descends from an upstream core) and the missing constraints.
* The new controller replaces three modules: `tau_sdram_ctrl` (825 lines), `tau_sdram_arbiter` (owner lock between the framebuffer master and the CPU bridge) and parts of the bridge's request handling. Budget (Tau V's estimate): under 2,000 ALMs and 4 M10K for six ports. The player has 4,622 ALMs and 36 M10K free (`t5-b899`: 13,858 / 18,480 and 272 / 308), so it fits with room, and the old three modules leave.

### Recommendations on Tau V's open points (for the owner)
1. **Fixed burst length 8, chained column commands, writes masked with DQM**, not full-page with BURST TERMINATE. It keeps the controller's grant granularity at 8 words, which is the strongest bound on an urgent scan-out request, and it needs no terminate timing. (Full page is simpler to write for long bursts but ties the bus for the whole request.)
2. **CPU port: keep today's single-word semantics first** (the mailbox and the data window through `tau_sdram_cpu_bridge` and `tau_sdram_wb_adapter`, proven by the 30-minute soak), with a **cache-line burst port as a later extension**; changing the CPU's contract and the controller in one step doubles the risk on the one unit.
3. **Address mapping: bank = bits 11:10, row = bits 24:12, column = bits 9:0** exactly as Tau V assumes; it is internal, so no firmware change.
4. **Clock plan:** the controller is parametric, the player stays at 100 MHz until a separate decision; no Talos or bridge changes for 133/150.

## 3. What the player needs on top of Tau V's list
A1 byte-enable single-word access with the latency of the idle case low (the CPU window); A2 the mailbox semantics and the `sdram_init_complete` signal (the firmware waits for it); A3 no hang or wrap on a request that crosses a page (the old controller's issue); A4 per-port counters readable through MMIO, plus the busy-cycle counter the Info page shows today; A5 the controller-boundary debug taps of `TAU_PHASE2_PROBE` as an optional build; A6 a build parameter that makes it behave like the old controller's timing for a fallback A/B on the one unit (a closed-page mode is already Tau V's optional parameter); A7 the second display buffer at word 1,048,576 and the stash rows keep their linear addresses.

## 5. Risks
R-C1 one Pocket unit and no SDC today: a controller that passes in simulation and fails on the board (mitigation: D-T06 acceptance, the old controller kept as a build option until the soak passes, the probe and the owner's warm soak). R-C2 the chip model is written from the same datasheet reading as the controller; two separate authors and the old controller's baseline run are the check. R-C3 request ordering between ports (a CPU read after an engine write to the same address): Tau V needs none between ports, the player's firmware fences with `FENCE`; keep that rule and test it. R-C4 timing closure of the engine's fill path at 100 MHz with a new front end (the last two fits had +1.1 to +1.4 ns slow-corner setup). R-C5 150 MHz is beyond what the rest of the player closes: keep it a parameter, never a default. R-C6 Tau V's numbers are model estimates (the study is theirs): the acceptance replay is the check.
