## 1. Headline

* **1,013 vectors** (779 on main's engine, 234 on Gallery's), 18 sets, all through the old engine with the protocol, retirement-order and acceptance checks armed. Vector verdicts: **857 IDENTICAL**, 59 carry IMP-TEXT-DARK, 74 IMP-RESERVED-NOOP, 17 OOD, 30 TIMING (bookkeeping, section 2.3), 1 PARAM-Q2, 0 IMP-FILL-NOLOSS (no vector makes two fill requests close together; the experiment of section 4 does), **0 UNAPPROVED** (a vector can carry several classes).
* **The contract, as the model reads it, agrees with the shipped engine on every legal-domain word of every vector.** The disagreements are in places no vector reached; the oracle experiments of section 3.3 found **8 UNAPPROVED-equivalent findings** (U1..U8; U9 is the approved IMP-FILL-NOLOSS case), triaged as: (a) contract gap or error 4 (GAP-25 fill of a line >= 360, the 2^16-period pattern of plan 2.1, GAP-05 and GAP-07 wording), (b) model bug 1 (GAP-09: the model clears `fill_seen`/`fill_done_line`, the engine keeps them; also a contract omission), (c) old-engine behaviour outside the legal domain 2 (GAP-16 rows past 2^19, Gallery's viewer with `FILL_WORDS` 512), (d) defect the owner should know 1 (GAP-29: the drawing buffer is changed while commands may be queued; `fw2` does it without a fence; shipped firmware can trigger it, packs cannot).
* **Q7:** the displayed buffer and flip pending survive the engine reset (bench: flip, reset, read: `disp` stays 1, a pending flip stays pending). Firmware does **not** depend on it: `fw2` never reads `DBUF_DISP` before its first `gfx_frame_begin`, writes `R_DBUF_CPU` only through `gfx_set_target`, and assumes buffer 0 at boot (static shadow). And the engine `reset` is `~pll_locked` (`core_game.vh`), asserted only at configuration, never by the CPU reset; so "survives reset" is unobservable in the product. **Recommendation: FREE** (either is conforming), firmware unchanged.
* **Text weights:** the engine's text arithmetic is exactly C-CHAR-3 (all 256 codes, both polarities, four scales, channel extremes: only IMP-TEXT-DARK differences). **The contract formula is right; `tools/derive_text_weights.py` models the engine wrongly** (8-bit bit-replicated mix). Refitted with the engine's arithmetic the dark table becomes `0 4 6 7 8 9 10 11 12 13 13 14 15 15 16 16`: it differs from the shipped table at **one** level (c = 5), not four, and the v0.1 "derived" table is *worse* than the shipped one on the real engine (mean |dL*| 1.980 against 1.949; the refit 1.898). The tool's `blend565` and the two table rows of C-CHAR-4 must change (section 5).
* **Costs:** the stub figures of contract table 7.1 are reproduced exactly by the harness (same stub). The realistic-path table (section 6) is new: it is the R4 reference the contract author could not run. Headline: constant writes cost one cycle per word on the real path (RECT 400 x 360: 168 k cycles against 1.8 k on the stub, so the stub is no cost model for RECT/BAR/RRECT); SBLIT costs 16.1 cycles per output pixel (BLIT 2.46), the measured baseline for D-T24 item 4; no command issued a bad request and no line was late. The per-tick estimate puts every meter's engine work at or below about 0.6 M of the 2.6 M clk_sdram cycles of a tick, and where the CPU waits (Chladni, Waterfall) it agrees with the DEV 196 to 198 fence times within a factor of 1.2 to 1.8: a new engine within +5 % per class (R4) keeps every 7.2 row within +5 %.

## 2. Method

### 2.1 What runs
* `tools/talos_v2_model/` (imported, paths fixed; `test_model.py` 292 checks green in the repository, `--fast` 290 checks in 19 s is wired into `make test-host`; the full generator plus test is `make talos-v2-model-full`, about 1.5 min). The repository's `gen_vectors.py` reproduces the author's 18 vector files **byte for byte** into `work/talos_v2_model/vectors/`.
* `sim/tb_talos_v2_diff.v`: one vector, translated by `run_diff.py` into port-level stimulus, through the old engine on the probe's functional stub (identical timing to `sim/tb_talos_v2_contract_probe.v`'s stub, with the full 2^25-word space paged). The SoC registers are emulated from `tau_soc.v` (held `FB_*`, `BLT_IDX/DATA` stepping, CLUT and corner-table index stepping, `TEXT_MODE`, `DBUF_*`, `FONT_IDX/DATA/CTRL`). It logs every memory word written with the push that wrote it, every dispatch and retirement with the command's stub cycles and request counts, every fill's line-buffer words, the engine outputs at every register read, protocol violations (request length 0 or above 512) and hangs.
* `run_diff.py` (manual `make talos-v2-diff`, about 4 min on 12 cores; `make test-rtl-talos-v2-diff` is an 11-vector self-test plus a comparator check that a one-column-short model is caught): compares final memory (every address written by either side), line-buffer contents per fill, register reads, final status, retirement order and accept/drop decisions.

### 2.2 Classification (plan section 3)
Per differing word, against the model reshaped one approved change at a time: equal to the model with the shipped dark table → **IMP-TEXT-DARK** (also when a later BLIT/COPY/CBLIT copied the text pixel onward: propagated); equal to the model reshaped to the old build (shipped tables, reserved opcodes drawing one RUN row, Gallery's always-on CORNERS/DSBLIT) → **IMP-RESERVED-NOOP**; written by a command outside its legal domain, by a command a reset abandoned (C-RST-2) or in a vector whose model flags a nondeterministic setting change (C-ORD-5) → **OOD**; a fill the old engine lost → **IMP-FILL-NOLOSS**; otherwise **UNAPPROVED**.

### 2.3 Two bookkeeping classes (not engine findings)
* **TIMING:** the model is transaction level ("the slowest legal engine": queued commands execute only at `wait_idle`, `fence`, `step` and the end). A register read or a fill taken while the model still held unexecuted commands, and push accept/drop decisions that differ because the old engine had already drained some of the queue, are not comparable. When accept decisions differ, the model is replayed with the old engine's decisions so everything after is still compared word for word. A `step` becomes "wait until the old engine has retired as many commands" in the bench. 30 vectors carry TIMING; all their memory words are still classified.
* **PARAM-Q2:** the one vector built with the derived light table (contract Q2 alternative), which the old engine cannot express.

### 2.4 Harness corrections made during development (recorded so nobody re-reads them as engine findings)
The first full run printed 19 UNAPPROVED vectors; all were harness artefacts and were fixed in the harness, not explained away: the bench numbered every push while the model numbers accepted pushes (attribution); the model's reset ends a memory stall, the bench did not (a hang); `step` was a fixed delay; words copied onward from an approved difference were counted against their copier. After the fixes: 0.

## 4. Settled open items

### 4.1 Q7 / C-DBUF-3 (the contract's one UNCONFIRMED rule)
Bench (`e_q7`): flip, vertical blank → `(disp, pending)` = (1, 0); reset → (1, 0); flip request → (1, 1); reset → (1, 1); vertical blank → (0, 0). **Confirmed: kept, and a pending flip is kept too.** Firmware: `fw2/platform/platform.c` reads only `DBUF_DISP[31]` at boot; `fw2/gfx/gfx.c` keeps `cpu_buf` as a static shadow starting at 0 and never writes `R_DBUF_CPU` before the first `gfx_set_target`; `gfx_frame_begin` reads `DBUF_DISP[0]` each time. The engine reset in the shipped integration is `~pll_locked` (`core_game.vh` line 918), separate from the CPU reset (`cpu_reset`, which clears the SoC's held `FB_*` and `FB_STALL` but not `dbuf_cpu_buf_r` or `text_light_r`, which have no reset branch). **Answer: FREE**; no firmware depends on it. Side note for the owner: after a CPU-only reset the hardware's `R_DBUF_CPU` and displayed buffer keep their old values while the firmware shadow restarts at 0 (blits go to buffer 0, rects to the hardware's choice) until the first frame begin; harmless today because the CPU is reset only at load.

C-DSB-1/-2 (80 vectors on Gallery's engine, seven self-chosen cases, key and blend on): IDENTICAL; the model's DSBLIT position map, taps and rounding equal Gallery's accumulator implementation.

## 5. Text weights (GAP-24, C-CHAR-3/-4)
**Engine arithmetic (`tau_talos.sv`, and confirmed by 62 V-CHAR vectors):** per channel, the 5/6/5 fields are mixed directly, `(fg*w + bg*(16-w)) >> 4`: exactly C-CHAR-3. The tool's `blend565` expands to 8 bits by bit replication, mixes, and truncates back to 565: a different arithmetic in 30.3 % of (value, weight) cases (281 of 576 theme pixels in the dark fit, 431 of 576 in the light fit render differently). Refit with the engine's arithmetic (36 weighted pairs each; same method, ends fixed, non-decreasing):
| table | c = 0..15 | mean / worst |dL*| on the engine |
|---|---|---|
| shipped dark | 0 4 6 7 8 10 10 11 12 13 13 14 15 15 16 16 | 1.949 / 6.45 |
| v0.1 "derived" dark (tool arithmetic) | 0 4 6 7 8 9 10 11 12 12 13 14 14 15 15 16 | 1.980 / 6.45 |
| **dark refit (engine arithmetic)** | **0 4 6 7 8 9 10 11 12 13 13 14 15 15 16 16** | **1.898 / 6.45** |
| light in use | 0 1 1 2 3 3 4 5 6 7 8 9 10 12 13 16 | 2.958 / 10.45 |
| v0.1 "derived" light | 0 1 1 2 3 3 4 5 5 6 7 8 9 11 13 16 | 2.334 / 6.35 |
| **light refit (engine arithmetic)** | **0 0 1 2 2 3 4 4 5 6 7 8 9 11 13 16** | **2.182 / 6.35** |
**Verdict:** the contract formula is right; what must change is the weight fit: `blend565` in `tools/derive_text_weights.py` (and `sim/test_derive_text_weights.py`, `TEXT_WEIGHTS_REDO_2026-11-25.md`) and the two derived rows of C-CHAR-4. IMP-TEXT-DARK then shrinks from four coverage levels (5, 9, 12, 14) to one (c = 5), and the D-T21 dark change becomes a one-step change at one level; Q2's alternative light table changes as shown. Not changed here (owner decision; tool, test and doc change together).

A second run with the CPU hammering the SDRAM (`run_gfx_cost.sh 1`) is recorded in the audit entry when it finishes.

### 8.4 D-T24 items 3 to 6: proposed rules
Baselines measured on the shipped engine with this harness (stub cycles unless marked realistic).

**Item 5 — every fill request served (C-FILL-3 becomes CHANGE).**
* Baseline: two requests less than about 400 clk_sdram cycles apart (the 400-word read time) → one fill, reported as the second line, its words partly the first line's; at 400 and more apart, both served. A request while a long command runs is served after the current request (wait ≤ 131 cycles, B-1178), but a second one in that window is lost too. The shipped scan-out asks one line per scanline (about 4,167 clk_sdram cycles), so only a doubled or jittered request triggers it.
* **C-FILL-3 CHANGE [IMP-FILL-NOLOSS, D-T24 item 5]:** "Every request is served, in order: a request seen while a fill is in progress, or while an earlier request waits, is queued (at least two outstanding requests); each served request writes its own line's words to its own half and reports its own line. Two requests for the same line may be served once (reported once)."
* Vectors: two requests 0, 1, 100, 399, 400 cycles apart (lines n, n+1 and n, n); three back to back; one during each long command class; fill-done order monitor. Mutants: M23 drop the second request; M24 report the first line for the second fill; M25 write the second fill into the first's half.
* Cost: one queued 10-bit line and a flag; no memory cost. Risk: the line-buffer half being drained by the scan-out could be overwritten if the engine serves a stale request late; the rule should add "a request older than one scanline may be dropped and counted" only if the scan-out contract allows it (open: ask the scan-out contract owner).

**Item 6a — wide rows (OPT-IN, capability bit 22, parameter `FEAT_WIDE`, default 0).**
* Baseline (BLIT, COPY, CBLIT, h = 2): width 127 → 254 words; 128 → 0 words written, **two zero-length write requests** (bad requests), 516 words read; 129 → 2 words; 200 → 144 (72 per row = 200 mod 128); 255 → 254; 256 and 384 → 0 words and zero-length writes. Stub cost 529 cycles for 127 x 2.
* **C-WIDE-1 OPT-IN [D-T24 item 6, capability bit 22]:** "With `FEAT_WIDE` = 1, BLIT, COPY and CBLIT accept `w` 1..511 with the result of C-BLIT-1/-2/-3, C-COPY-1 and C-CBLIT-1 for every column; C-ORD-1 holds for the whole row (every source word of the row is read before any destination word of the row is written). SBLIT and DSBLIT keep the 127 clamp (C-SBLIT-2 PINNED). With `FEAT_WIDE` = 0, `w` above 127 is out of domain (C-GEN-2), as v0.1."
* **C-WIDE-2 PINNED [C-MEM-5]:** "no request of length 0 or above 512 in either setting."
* Vectors: w = 127, 128, 129, 255, 256, 400, 511 for each of the three commands, with key, blend, overlaps left/right inside a row, stride 0, base near 2^25. Mutants: M26 width modulo 128 with the bit set; M27 a wide row read in chunks written chunk by chunk (breaks the right-overlap case).
* Cost: a 512-word row buffer (one M10K instead of the 128-entry MLAB pair: watch the M10K count, 274 to 281 of 308 used) or row chunking with read-all-then-write over chunks (needs the same storage). Throughput per word equals the 127 case (realistic table: BLIT 127 x 16 row cost). Risk: the blend pipeline's second read port (B-327 two MLAB copies) doubles a 512-word buffer; fit and timing must be re-proved; firmware's 120/127 splitting stays valid either way.

**Item 6b — overlap-safe copy (OPT-IN, capability bit 23, parameter `FEAT_OVERLAP`, default 0).**
* Baseline (64 x 12, one command): COPY and BLIT left (-1 word), right (+1), right (+5), up (-1 row): **identical to a memmove** (the row is buffered, rows go top-down); down one row: 704 of 768 words differ; down three rows: 576 of 768 differ. The model reproduces all six exactly.
* **C-OVL-1 OPT-IN [D-T24 item 6, capability bit 23]:** "With `FEAT_OVERLAP` = 1, a BLIT or COPY whose destination rectangle overlaps its source with the destination below (in rows) produces the memmove result: the result equals reading the whole source rectangle before writing any destination word. Other overlaps already give the memmove result (C-ORD-1). CBLIT, SBLIT and DSBLIT unchanged." Implementation free (bottom-up row order is one way, item 3).
* Vectors: the six cases above for COPY and BLIT, with key and blend on, strides 0/511/513, and with `FEAT_WIDE` both ways. Mutant: M28 top-down order kept with the bit set.
* Cost: none in memory traffic if rows run bottom-up (same reads and writes); one comparator at dispatch. Risk: with stride 0 or strides that differ between source and destination "below" must be defined on addresses, not rows: the rule should say "when the first destination word lies after the first source word and the rectangles share a word".

**Item 3 — reverse row order / negative stride, designed in, not wired (CHANGE-ready, capability bit 24 proposed).**
* Baseline: strides are 10-bit unsigned (0..1,023), rows are always processed top-down; no field selects anything else.
* Encoding proposal: **`R_FB_GO` bit 23 → new port bit `cmd_rev`** (free today: bits 31..23 are unused by every opcode; `subop` uses 22..17). It costs one queue bit (95 of the 120 available with ESC). An ESC sub-opcode instead would cost a sub-opcode per command it modifies and would not combine with BLIT's existing operands; a spare `glyph` bit would differ per opcode (CHAR and BAR use it). Proposal text:
* **C-REV-1 PINNED-AS-ZERO [D-T24 item 3]:** "`cmd_rev` = 0 for every shipped command; with `cmd_rev` = 0 behaviour is v0.1 exactly." **C-REV-2 FREE (built, unused):** "with `cmd_rev` = 1, BLIT, COPY and CBLIT process rows `h-1` down to 0 (source and destination row addresses step by minus the stride; equivalently a negative stride of the same magnitude); every other opcode ignores the bit. Firmware does not set it until the owner wires it (D-T12(c))." Capability bit 24 = built.
* Vectors (when wired): the overlap-down cases with `cmd_rev` = 1 give the memmove result; rows land bottom-up in the write log. Mutant: M29 the bit ignored. Cost: one adder sign per row step (zero memory traffic); the Waterfall vertical fullscreen tick (450 k cycles) is the use case. Risk: a capability bit that firmware tests but no command uses: state "bit 24 means `cmd_rev` is honoured".

**Item 4 — burst SBLIT (speed only, FREE).**
* Baseline: 7.04 stub cycles per output pixel at every scale (one single-word read request per output pixel, one streamed write per row); BLIT 2.08. Realistic path: **16.1 cycles per output pixel** (SBLIT 40 x 40 at 2x: 102,887), BLIT 2.46.
* **C-SBLIT-5 FREE [D-T24 item 4]:** "how SBLIT reads its source is not contractual (one request per pixel, per source row or per span); the output is C-SBLIT-1..4 exactly; the R4 ceilings of SBLIT apply." Pixel-identical: no class needed (V-SBLIT, 164 vectors IDENTICAL, is the gate).
* Vectors: V-SBLIT unchanged plus a source row crossing a 1,024-word page and a 2^25 wrap. Mutant: M30 a burst that reads one word short at the row end. Cost: a source-row buffer of 127 words (the existing row buffer is busy with the output row: a second one); the burst needs `ceil(w_src)` reads per source row instead of one per output pixel. Expected: 2x upscale of 40 x 40 from 45,201 to about 9 k stub cycles. Risk: the fill-wait bound (C-FILL-2) with longer bursts (keep each request <= 128 words) and one more MLAB.
