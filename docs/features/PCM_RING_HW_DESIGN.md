# Gapless boundary, decision and design: a hardware PCM ring reader (B-740, 2026-10-14)

**Status: DESIGN, nothing built.** Follows `GAPLESS_SPEC.md` sections 8 and 9 (the adversarial review: a firmware drain protects nothing in the loops that run without calling it). Evidence labels: [HW] measured on a Pocket, [READ] source, [EST] estimate.

## 1. The audit the review asked for, and what it says
`poll_input()` is called from every wait that services the player (FIFO waits, refill spins, the main loop), so **the stalls POLL GAP counts (20 ms or more between two calls) are exactly the places a drain hooked into `poll_input()` could not run.** [HW, DEV 119 to 121, same boot, before and after one natural track end plus a few other actions]: the 46-300 ms bucket grew from 2 to 14 and the 20-46 ms bucket from 1 to 43. A natural end is not one stall but about a dozen, each longer than the FIFO (46 ms); they sum to the measured 470-540 ms gap (LOAD MS 163-172 ms of it: slot settle about 80 ms of 30 ms sleeps, the head read, TIM1 decode about 85-100 ms, prefill; the rest the flush, its 44 ms fade-in and the first frame).
Making a firmware drain work would mean finding and hooking every one of those loops (slot-open settle sleeps, the TIM1 decode, chrome repaint at the track switch, library and playlist work...) and keeping each under about 40 ms for ever after, in a file that changes every week. The POLL GAP row with its new addresses can find them, but nothing prevents the next change from adding another.
**Decision: put the drain in hardware.** The CPU only WRITES decoded pairs into a PSRAM ring and bumps a write pointer; an RTL reader pulls them into the audio FIFO on its own. After that no firmware stall can underrun the audio until the ring itself is empty. The ring then only has to cover the longest load (about 600 ms) plus margin: **1 s** (172 KiB at 44.1 kHz, 188 KiB at 48 kHz), not 2 s.

## 2. Hardware
**`tau_pcm_ring.sv`** (new), a third client of the PSRAM controller next to the CPU window and the instruction fetch (`tau_psram_bus` already has the two-client arbiter of B-047, both read paths proven; the reader is read-only):
- Registers (MMIO, free slots after 0x164; exact addresses in `docs/MMIO_ALLOCATION.md`): `RING_BASE` (PSRAM word address of the ring), `RING_WORDS` (size in pairs), `RING_WPTR` (written by the CPU: pairs put so far, a free-running 32-bit count), `RING_RPTR` (read only: pairs the reader has pushed), `RING_CTRL` (enable, flush/reset, underrun-hold), `RING_STATUS` (empty, running, guard).
- Behaviour: while enabled and `WPTR != RPTR` and the audio FIFO level is below a threshold (say 1,536 of 2,048 pairs, one pair per request), read the word at `base + RPTR % size` and push it into the FIFO through the same port the CPU's `R_AUDIO` write uses (so the FIFO sees one writer at a time: the CPU path is disabled while the ring is enabled, or arbitrated by the enable bit). One PSRAM read is 32 cycles [HW, KB-040]; 44,100 pairs a second is about 1.4 M cycles of 66.7 M: 2% of the PSRAM, and the reader yields to the CPU and fetch arbitration like the second client does.
- Flush: `RING_CTRL.flush` sets `RPTR = WPTR` and clears the FIFO (the existing flush), so `pcm_flush()` stays one write.
- Volume, fade and the gain stage: unchanged. They act on the FIFO OUTPUT (the hardware gain stage, B-615) or on the push; with the ring the software gain path is retired (`HW GAIN` owns it in every current build; the software path remains only for a bitstream without the stage, which then cannot use the ring either: the ring feature bit says so).
- Failure: a missing feature bit, a guard hit or a failed boot proof switches the ring OFF and the firmware pushes straight into the FIFO as today (KB-039: prove at runtime, switch off, do not fall back mid-stream).
- Cost [EST]: about 300 ALMs, no M10K, no DSP; one more PSRAM client in the arbiter (the arbiter, not the reader, is the timing risk: B-050's G3 builds closed with +0.8 to +1.1 ns setup).

## 3. Firmware
- **Put** (`pcm_ring_put`, hot, small): write the pair to `ring[wptr % size]` through the PSRAM window (32 cycles a write), bump `RING_WPTR` once per frame. Producer waits (spinning `poll_input`) only when the ring is full (`wptr - rptr == size`).
- **Heard position** = decoded position minus (`WPTR - RPTR` + FIFO level). Clock, progress bar and seek use it (section 8 of the spec).
- **Boundary (G2) becomes simple:** at end of file, do NOT flush; open the next track and start decoding into the same ring behind a boundary marker. The marker is a position (the `WPTR` value at the boundary) kept in a small firmware queue; the UI, the ReplayGain target and the position clock switch when `RPTR` passes it (checked in `ui_draw_dynamic_cold`, no hardware needed). Same-rate boundaries only; a rate change waits for the ring to run dry (G3).
- **Meters** (the 2 s early problem, spec section 8): the hardware spectrum and wave taps read the FIFO output and are already heard-aligned; the software peak/scope feed moves to a heard-position read: when `RPTR` advances by 1,152 pairs, read that chunk back from the ring (1,152 x 32 = 37 k cycles per 26 ms, about 2% CPU) and call `meters_feed` on it.
- **Info rows** (new, Diagnostic Build): RING fill now / minimum, wptr and rptr, underruns while non-empty (must be 0 in a boundary test).

## 4. What it fixes and what it does not
Fixes: every firmware stall shorter than the ring fill (seeks excepted, they flush), not just the ones we found; the natural-end gap if the boundary is gapless; the 2.3-5 s cover decode no longer needs to be polite to the audio. Does not: a manual change keeps its flush and 44 ms fade-in (by design), the tempo path keeps its own staging ring (ring off while tempo is active), the lead is short after a seek or start (section 2b of the spec: fast fill for the first seconds).

## 5. Build order and gates (same discipline as the other units)
1. **Host model** `tools/lab/pcm_ring_model.py` + C golden model and vectors: random put/flush/underrun sequences against a FIFO model; the stream pushed equals the stream put, no pair twice, none lost, flush exact. (`fw/pcm_ring.h`, already built and tested, is the software twin of the pointer logic and is reused for the firmware put side.)
2. **RTL** `tau_pcm_ring.sv` + testbench + mutants (pointer wrap, flush, FIFO-full, arbiter starvation) + wired in `mp3_soc.v` behind `PCM_RING_ENABLE`/`TAU_PCM_RING`, registered in the qsf.
3. **Synthesis-only check** (a third PSRAM client; the RAM-inference lesson of B-223..B-228 does not apply, no new array), then a **two-seed fit** with the shipped macro set plus `TAU_PCM_RING=1` (about 1h40 to 1h45 per the family's history).
4. **Firmware** behind `TAU_PCM_RING_FW`, boot probe + proof, put/drain removal from the push paths, flush, heard position, meters, Info rows; `sim/test_pcm_ring_fw.py` host proof of the put side and the position arithmetic (pause, flush, seek).
5. **Pocket:** G1 alone first (no boundary): same sound, RING min fill, no new underruns, hard FLAC clean; then G2.
