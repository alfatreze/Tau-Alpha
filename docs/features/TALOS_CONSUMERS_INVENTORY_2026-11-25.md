# Talos consumers: who issues which engine commands (2026-11-25)

Input to the Talos v2 scoping (`TALOS_ENGINE_V2_SCOPING_2026-11-25.md`, decision D-T18: every command is kept). **Method:** static search of the owner's projects under `DEV PROJECTS/` for the engine's files and command wrappers (`tau_talos`, `tau_gfx`, `mp3_fb`, `OP_*`, `fb_*` and `gfx_*` calls). **Not done:** no build configuration, runtime trace or opcode histogram of any other core was read or run; counts are call sites in source, not frequency.

## Looked at and NOT a consumer
* **Dethrace-Rewired:** it vendors Tau Alpha under `third_party/Tau-Alpha` (a reference copy, one tracked entry) and no file of its own build includes the engine; its decision D-003 (2026-11-17) rejected Talos for reuse (openfpgaOS already has a GPU; `PLAN_REVIEW_2026-11-17.md` R1).
* Tau-blocks, tau-cart, tau-web, Tau codecs (a few files, text only), Dethrace-Clash, Oregon Trail Pocket, SpectrumDeck, FreePGA, NeoCalc, PicoDS, the Saturnix projects: no engine file or command call found. Tau Gallery has no working copy under `DEV PROJECTS/`; it was read from its archive on MONSTER (see its row above).

## What this means for the rewrite
1. **All ten commands are in real use somewhere in the family, and Gallery adds two more.** RUN (2 call sites), COPY (10), RRECT (7) and the CHAR scales are issued by the old-player lineage that Tau V and Tau Μ still run, even though Player 2 does not. This supports D-T18: do not drop any command.
2. **Tau V is a future consumer of the new engine.** Its plan is to import the rewritten graphics stack at a stable tag, so the compatibility policy (no regressions; improvements behind a capability bit or ABI revision) protects a second firmware, not only Tau Alpha's. Its old-player drawing code is the realistic test load for COPY, RRECT, RUN and the CHAR scales: its firmware is the first conformance input to collect.
3. **Tau Gallery already extends the engine, and that changes the contract.** It added opcodes **10 (CORNERS) and 11 (DSBLIT)**, a viewer-fill mode and a pixel doubler to its copy of `tau_talos.sv`. The new engine's opcode map must leave 10 and 11 free for those two (or adopt them natively), so that Gallery can import the rewrite without a renumbering; the 4-bit opcode field still has 12 to 15 free. Adopting DSBLIT, CORNERS and the viewer fill into the common engine, behind a capability bit, would let Gallery drop its fork of the file; that is an owner decision (it also means two projects' rendering rules must agree). Gallery 1.0.0 ships the inherited engine text too, so the provenance goal covers Gallery once it imports the replacement.
4. **Tau Reader is a planned consumer of the SoC interface and the Talos UI path** (see its row; first listed wrongly as "text only", corrected the same day). Keep the engine's MMIO registers, queue, status and fence interface stable (the scoping's B-lean/B-full both do), and tell Tau Reader which MMIO ranges the new engine uses; its plan expects the "parked row-job, command-ring and extended-glyph proposals" NOT to exist, which matches D-T12. Reader's own glyph blitter is its own code and out of scope here.
5. **Copy-once-then-diverge:** Tau V and Tau Μ take files by hash from a tag, so a rewrite does not break them until they choose to import it; the risk is at that import, not now.
6. **Open, cheap to measure:** the real frequency of each command in Tau V's firmware (a trace or the per-opcode counters of the engine's `R_GFX_COUNTS`), whether Tau V's drawing code passes against the new engine in a host test, and whether Tau Μ is still active, and whether Tau Reader will use Talos commands (its firmware issues none today), the per-call counts of Gallery's firmware, and a line-by-line diff of Gallery's engine against the pin to list every behaviour it changed.
