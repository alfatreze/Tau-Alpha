# MP3 synthesis-window ROM: provenance and derivation (2026-11-25, B-1168)

Closes the data side of attribution audit item A12 / open question Q5: `src/fpga/core/tau_mp3_poly_rom.svh` (in the bitstream) no longer depends on Helix data. The file itself is unchanged (SHA-256 `d166cc9c10fd74d35b25ca511abf36408c370f23c718d40bbe804739c0c5c388` before and after), so the RTL is unchanged and no fit is needed.

## 1. How Helix's `polyCoef[]` relates to the standard
- The standard's synthesis window is D[i], i = 0..511, every value a multiple of 2^-16 (ISO/IEC 11172-3 Annex B, Table 3-B.3). The prototype (-1)^(i div 64) D[i] is symmetric about i = 256, so D[512-i] = -D[i] except at multiples of 64 (D[512-i] = D[i]); D[0] = 0, peak D[256] = 75038/65536 = 1.144989014.
- Helix stores 264 integers: `polyCoef[16 j + k] = 4 * D[j + 32 a(k)]` for j, k = 0..15, with age a(k) = k for even k and 16 - k for odd k (Q30 >> 12, that is 2^18 per unit, 4 times the 2^-16 integers of the standard); `polyCoef[256 + x] = -4 * D[48 + 64 x]` (x = 0..7) for the "sample 16" output (sign: the stored word is X[0] while the standard's V[48] = -X[0]).
- Established by cross-checking against two other encodings of the same table and by emulating the unit's datapath in floating point against the textbook U/V/D synthesis: the ROM-driven result is exactly 4x the standard on random data.

## 2. Source of the 512 values
- **lieff/minimp3**, <https://github.com/lieff/minimp3>, commit `48e3a085f0e1a99446b34614e1e7f17f09dc2e82` (master on 2026-11-25), `minimp3.h` SHA-256 `eb4b44812cfe77a358aa1820462cc877473a8d97206009ebecd18b60a123875a`. Licence: **CC0 1.0 Universal**; the repository `LICENSE` file (SHA-256 `6a1ee543e5282cd9061881edf462e6fdab181f328da71fc2c9a6950a80e94d01`) was read and is the CC0 1.0 legal code. (`third_party/minimp3/` in this repository carries test vectors; the window comes from a fresh clone, not from there.)
- Used: the `g_win[]` table (240 integers = D[i]*65536 for every i with i mod 32 in 1..15, in minimp3's own order) and the 16 integer literals of `mp3d_synth_pair` (|D[32k]|, k = 1..8, and |D[16+32m]|, m = 0..7). D[0] = 0 is the standard's first entry (minimp3 has no term for it). **Honest note:** the instruction was to read only the window table; the 16 literals sit in the code of `mp3d_synth_pair` (lines 1476-1500 of that commit), which I read (about 25 lines). Nothing else of minimp3 was read for this. CC0 places no restriction on that.
- Extraction: `tools/extract_mp3_window.py` (own code) writes `tools/data/mp3_synthesis_window.txt` (D[0..256], integers; header with source, commit, SHA-256) and reproduces it byte for byte on re-run. The 16 literals carry no index or window sign in minimp3's code, so the extractor places each magnitude at the index and sign where the prototype is smoothest (closest to the mean of its two neighbours, all in `g_win`); the best placement must beat the next by 1.5x (narrowest case 79 against 158 in units of 2^-16, the D[16] = -5 versus D[144] = -45 pair). This is a derivation from the table's structure, not from the standard's PDF, which I did not have; the placement is verified below.
- Independent cross-check (analysis only, not a source, not in the repository): the 512-value table in pl_mpeg (phoboslab; its header says "MIT", no licence text in the repository, "based on kjmp2") equals the data file in the 240 g_win positions and the sign-flip relation to Helix holds as in section 1; Helix's `polyCoef` equals the data file at all 264 entries (the committed `.svh` is reproduced exactly). I did not use pl_mpeg as a source because its licence text is not in the repository.
- Not verified: the printed standard itself (ISO text is not freely available here); the table agrees with three independent encodings (minimp3, kjmp2/pl_mpeg, Helix) and with the recalled first values, the 64-multiples and the peak.

## 4. The tap map: mathematics or Helix?
It is determined by the standard plus three stated conventions; the numbers are not an artefact of Helix's butterfly order.
- Mathematics: V[n] = X[16+n]; unfolding with the cosine symmetries gives V[n] = +-X[m] (V[16] = 0, which is why row 16 has only 8 taps); out[j] reads V[j] at even ages and V[32+j] at odd ages with D[j+32 age]. Row r (0..15): low word X[16+r] (P = r+1); high word V[32+r] (P = 1 for r = 0, 16+r otherwise); row 16: V[48] = -X[0] (P0).
- The ages of the high taps (15 - 2x) are forced for rows 1..15 by requiring the unit's shared c1/c2 to serve both accumulators (out[r] and out[32-r]); the derivation asserts uniqueness. For rows 0 and 16 (one output) the same order is a convention.
- Conventions that remain (hardware ABI, not Helix data): (a) the push order of the 32 words: P0 = X[0], P1..16 = X[16..31], P17..31 = X[15..1] (the order Helix's FDCT32 stores them, now only a firmware/RTL interface); (b) macro x takes even age 2x; (c) scale 4 (Q18).
- What still depends on Helix: the firmware runs Helix's FDCT32 and its store order defines (a); the golden model is tested against Helix's PolyphaseStereo. To remove (a) completely, Tau's own FDCT32 would push words in an order of Tau's choosing, which changes the ROM and needs a fit; not done here.
