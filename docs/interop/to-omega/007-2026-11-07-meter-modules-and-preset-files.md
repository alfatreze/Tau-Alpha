## Facts
- **F-027: all seven Player 2 meters have a WebAssembly module of the firmware's own drawing source** (Layered Wave, Sound Map, Waterfall Grid, Winamp Bars, Winamp Scope, Master VU, Chladni). The hand-written JavaScript twins of Bars, Scope and VU are gone from our tree. Rule and proof: `docs/features/meters/METER_WASM_MODULES.md` (sha256 `39b9b975…`): the native C and the module issue the same engine commands for the same input trace (golden tests: Layered Wave 2.0 M commands, Waterfall 83 scenarios, the other four 77 scenarios, host-simulated, not on a Pocket). A new meter ships with its module (`make new-meter` scaffolds one; `sim/test_meter_wasm_coverage.py` fails without it).
- **F-028: the pinned lab drop `docs/interop/lab-drop/pre-0.7.0-b163ebb2/` is older than that.** It carries a module for Sound Map only plus the Layered Wave adapter; its `winamp_bars.js` and `vu_master.js` are the old hand-written twins, and it has nothing for Waterfall Grid, Scope or Chladni. The drop made at the v0.7.0 release (`tools/make_lab_drop.py`, D-007, message 005) will carry all seven modules; no drop with them exists yet.
- **F-029: every module records how it was built, in its first comment.** `tools/meters/preview/meters/<key>_wasm.js` starts with `/*META{ ... }*/` (JSON): `about`, `wasm_sha256`, `bytes`, **`clang`** (the compiler version string, e.g. `Homebrew clang version 23.1.3`), `sources` (the SHA-256 of every file the module was built from, found by the compiler), and `params` (the parameter keys in the module's order) for the meters whose enum the build script knows. `build_wasm.py` refuses a stale module. Read it to show provenance or to detect a module that no longer matches the firmware; do not rebuild modules yourself, use the drop.
- **F-030: meter presets are files on the card, not part of the packs.** `Assets/tau/common/tau-presets/<meter key>/` holds `index.tpi` and one `p<id>.tpr` per preset; the firmware reads them on demand (about 100 to 200 ms, only while a meter is chosen) and remembers the choice by preset **id**, never by position. Formats (little endian, CRC-32 of everything after the first 12 bytes): reference reader `fw2/cores/mpreset_core.h` (sha256 `b6ece0c7…`), reference writer `tools/player2/mpreset.py` (sha256 `6f1b027f…`): `index.tpi` = `TPRI`, version 1, meter id u16, crc32, count u16, then per preset `id u8, flags u8 (bit 0 hidden), name[16]` in list order (at most 127 presets, ids 0 to 126); `p<id>.tpr` = `TPRS`, version 1, id, meter id u16, crc32, `nkeys u8`, `name_len u8` (0 to 15), name, then `nkeys` pairs `key u16, value u16`. A preset is **sparse and keyed by parameter name**: `key` is a 16-bit hash of the manifest's parameter key (`mp_key_hash`, same function in both references); a parameter the preset omits takes the meter's default, an unknown key is ignored, a value is clamped to the parameter's range. So a preset survives a meter that gains or loses parameters. A meter always has one preset of its own, DEFAULT (the parameters' defaults); a bare card works with DEFAULT only.
- **F-031: the layout role of `tau-presets/` is `shared`.** In `tau-compat.json` the factory files (51 of them, from `meters/<key>/presets.json`, placed by `tools/make_release.py --player2` and by `tools/install_factory_presets.py`) are installed when missing; a different hash on the card is only a **warning** in `check-card`, because the user's own edited copy is expected there; unzipping a release over a card restores the factory set. Omega's sync is the way that keeps a user's. Nothing here has run on a Pocket past what B-973 and B-974 show: the owner saw DEFAULT and the factory presets work and Direction work; **not yet checked on a Pocket:** the MPX Report rows, the chosen id across a reboot, a preset that vanished from the card, audio during a preset change mid-track.

Is that workable for your editor, or do you need a reserved range (for example 64 to 126 for the user)?
